# Multilingual support

Queue Master ships with **English (`en`)** and **Polish (`pl`)**. Language affects four different
kinds of text, and they are stored in different places:

| What | Where it lives | Who edits it |
|---|---|---|
| UI strings (buttons, labels, errors) | `frontend/i18n/en.json`, `pl.json` | Developers |
| Category names | `Multilingual_Text`, `module_name = categories` | Admin panel |
| Print template, weekday labels | `Multilingual_Text`, `module_name = multilingual_settings` | Admin panel |
| Logos | `uploadsPath/logo/<lang>/` | Admin panel |

The **default language** is the global setting `locale` (**Admin → Settings → Other**). It is what
every screen falls back to.

---

## How the language is chosen

### Web app (Next.js) — cookie based

`frontend/apps/web/i18n/request.ts`, using `next-intl`:

1. Read the **`locale` cookie**. If it holds a supported code, use it.
2. Otherwise fetch the global settings and use `locale` from there.
3. Otherwise fall back to `en`.

The flag switcher (`components/LanguageSwitcher.tsx`) sets the cookie and calls `router.refresh()`,
so the server re‑renders in the new language.

> [!NOTE]
> The `locale` cookie is deliberately set with a **very short lifetime (10 s)**. A visitor's choice
> applies to the pages they are looking at, and the browser then falls back to the configured
> default. This suits shared/staff machines: nobody inherits the previous person's language. If you
> want a sticky preference, raise `maxAge` in `LanguageSwitcher.tsx`.

The cookie is read **server‑side**, so translations are rendered on the server — no flash of
untranslated content.

### Kiosk — in‑memory, auto‑resetting

The kiosk does not use cookies. `i18next` holds the current language in memory:

- It starts in the global `locale`.
- Flags switch it instantly.
- It resets to the default **60 s after the last interaction** (`INACTIVITY_TIMEOUT`), and
  immediately after a ticket is issued — so the next client always starts from the default.
- The chosen language is **saved with the ticket** (`Client.language`), which drives both the print
  template and the voice announcement.

### TV

Follows the global `locale`. If **TV auto switch language** is enabled, it switches to the language
of the client currently being called, so the announcement and the screen match.

### Backend

Endpoints that return translatable text return **all languages at once**
(`{ "en": "...", "pl": "..." }`); the client picks. There is no `Accept-Language` negotiation.

## Adding a new language

Using German (`de`) as the example. There is no single switch — the code is written so no logic
depends on a *specific* language, but the language has to be declared in each layer.

### 1. Backend — the `LangCode` enum

`backend/prisma/schema.prisma`:

```prisma
enum LangCode {
    en
    pl
    de
}
```

```bash
cd backend && yarn prisma migrate dev --name add_german_language
```

This is all the backend needs. The global `locale` setting takes its allowed values from
`Object.values(LangCode)`, multilingual settings iterate over the enum, and logo endpoints validate
against it — they all pick the new value up automatically.

### 2. Shared frontend enum

`frontend/packages/shared-utils/src/types/LangCode.ts`:

```ts
export enum LangCode {
    en = "en",
    pl = "pl",
    de = "de",
}
```

Keep it identical to the Prisma enum. The admin panel renders one input per `LangCode` value, so
category names, the print template and the weekday labels get a German field with no further work.

### 3. Translation file

Copy `frontend/i18n/en.json` to `frontend/i18n/de.json` and translate it. Keep **all** keys — a
missing key falls back to English in the kiosk (`fallbackLng: "en"`) and shows the raw key in the
web app.

Add the language's own display name to every translation file (the key referenced by
`langLabelKey`), e.g. `"german_name": "Deutsch"` in each of `en.json`, `pl.json`, `de.json`.

### 4. Web app

- `frontend/apps/web/i18n/request.ts` — add `"de"` to the `locales` array.
- `frontend/apps/web/i18n/langLabels.ts` — add the `LangCode.de → "german_name"` entry.
- `frontend/apps/web/components/LanguageSwitcher.tsx` — add the flag
  (`flag-icons/flags/4x3/de.svg`) and a click handler.

### 5. Kiosk

- `frontend/apps/kiosk/src/ui/i18n.ts` — add `"de"` to `supportedLngs`.
- `frontend/apps/kiosk/src/ui/components/LanguageSwitcher.tsx` — add the flag and handler.

> [!IMPORTANT]
> **Do not forget the IPC path.** The kiosk does not bundle translations into the renderer; it asks
> the main process for them over IPC (`electronAPI.getTranslation(lang)` →
> `handleGetTranslation` in `src/electron/main.ts`), which reads `i18n/<lang>.json` from disk.
> The whole `frontend/i18n/` directory is copied into the package by `electron-builder.json`
> (`extraResources`), so a **new file is picked up automatically — but only after a rebuild**.
> If the kiosk shows raw keys for the new language, this is why: the JSON never reached the
> packaged app.

### 6. Content

Then, in the admin panel:

- a **name for every category** in the new language — otherwise its button is blank on the kiosk;
- a **print template** in the new language — otherwise those clients get a placeholder ticket
  ([printing](printing.md));
- **weekday labels** in the new language, if you use opening hours;
- optionally **logos** for the new language.

## Conventions for contributors

- Never branch on a specific language code. Iterate over `LangCode` / `locales`; adding a language
  must never mean touching business logic.
- Never hardcode a user‑visible string in a component — add a key to the translation files.
- Data models carry the whole translation map (`{ en: "...", pl: "..." }`), not a single resolved
  string.
